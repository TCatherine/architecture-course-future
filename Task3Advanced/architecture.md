# Описание целевой архитектуры 

Документ описывает диаграммы [c4.drawio](c4.drawio) и объясняет принятые решения. 

## 1. Идея

1. **Домены слабо связаны и владеют своей логикой:** 
	- Домены развёртываются в изолировано, взаимодействуют асинхронно через события. Бизнес-логика живёт в сервисах домена-владельца, шина событий ничего не знает о логике, только обладает информацией о контрактах событий.

2. **Легаси выводится через мосты, а не «большим взрывом»: 
	- DWH и Camel работают как временные мосты совместимости.

## 2. Описание контейнерной схемы

### Доменные компоненты

- **Клиники:** 
	- сервисы пациентского потока (запись, приём, биллинг)
	- защищённый медконтур
- **Финтех:**
	- сервисы счетов/платежей/кредитов 
	- антифрод на потоках транзакций
- **ИИ-домен:** 
	- ML-инференс 
	- feature store
	- MLOps; 
- **Головной офис:** 
	- ERP/HR
	- инвентаризация
	- финансовая консолидация. Новые направления (фарма, электроника, регионы) подключаются как новые домены по  — без доработки чужих систем.

**Новые домены**: новые направления (например, регионы) подключаются как новые и независимые домены по стандартному контракту: события + схемы без изменений других доменов.

### Событийная платформа

Состоит из следующих компонент:
- Kafka (доменные топики, партиционирование по ключу агрегата)
- Schema Registry (версионируемые контракты)
- Flink (потоковая обработка)
- CDC-коннекторы Debezium из легаси

### Дата-платформа и витрина

Состоит из следующих компонент:
- Каталог данных (DataHub) 
- Система управления соыбтиями и данными (Lakehouse + S3 + Iceberg)
- Потоковые NRT-витрины  (ClickHouse)

### Легаси часть

Состоит из следующих компонент:
- DWH SQL Server 2008 - источник CDC на переходный период;
- PowerBuilder заменяется веб-интерфейсами доменов; 
- отчёты Power BI мигрируют в портал;
- Camel — см. ниже.

## 3. Миграций функций Camel

Kafka не заменяет ESB - это брокер, а не интеграционная платформа. Функции, которые сегодня выполняет шина Camel, при её выводе явно перераспределяются:

| Функция в Camel                  | Куда переходит                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **Форматно-логический контроль** | Структурный контроль - Schema Registry. <br>Бизнес-валидация - домен-продюсер владеет данными и отвечает за их корректность до публикации. |
| **Пакетные трансформации**       | Трансформация происходит после доставки, в слое данных (Spark над Lakehouse)                                                               |
| **Потоковые трансформации**      | На границах доменов, в их адаптерах, а не в центральном компоненте                                                                         |
| **Маршрутизация **               | Топология топиков + pub/sub                                                                                                                |
| **Паттерны надёжности **         | DLQ, retry у консюмеров; transactional outbox у продюсеров                                                                                 |
| **Интеграционная логика**        | Тонкие адаптеры к внешним системам на границе домена-владельца интеграции                                                                  |
| **Бизнес-логика**                | Полностью уходит в bounded contexts доменов                                                                                                |
